## Security Architecture (Verified ✅)

### Multi-Layer Protection

```
1. Prefilter Escalation (deterministic, regex-based)
   ↓
2. Affirmation Tripwires (answerable, logged, marker stripped)
   ↓
3. Advisory Judgment (model-assisted, never produces "allow")
   ↓
4. Durable Receipts (append-only ledger, tamper-evident)
   ↓
5. Master Switch (root-owned, fail-closed)
```

Each layer is independent; failure of any layer = denied.

### P1-03: Prefilter Deterministic & Non-Bypassable ✅

**Location**: `src/hooks/prefilter.ts:1042-1127`

**Protected Patterns** (regex-based):
- Pipe-to-shell: `| sh`, `| bash`, `| python`, etc.
- Destructive: `rm -rf /`, `mkfs`, `dd if=`, etc.
- Normalization: Strips quoting, `$IFS`, `$()`, backticks (lines 15-23 in `deterministic.ts`)

**Verification**: ✅ `tests/enforcement/deterministic.test.ts`

**Residual Risk**: Undocumented shell features may evade regex (e.g., POSIX `set -o`, rare builtins)

## Known Limitations (Accepted Risks)

### L1: Port Squatting (Multi-User Hosts)

**Risk**: Untrusted user binds port 10522 before daemon → receives hook payloads

**Mitigation**: `JEV_DAEMON_DISABLE=1` (process-per-hook, pipe transport)

**Status**: Documented (SECURITY.md), acceptable for single-user machines

---

### L2: Redaction Best-Effort

**Risk**: Shaped-value detection catches known patterns (sk-*, ghp-*, PEM), but natural-language secrets may slip through

**Status**: Consistent with threat model (SECURITY.md)

---

### L3: Non-Cryptographic Receipts

**Design**: Tamper-evidence via hash fingerprints, not cryptographic signing

**Trade-off**: Sufficient for audit trail; not proof of authorization

**Status**: Explicitly documented (receipt-validation.ts:28)

---

### L4: Live Model Integration Not Observable

**Gap**: Hook→judgment→closure→ledger round trip cannot be observed without production API key

**Status**: Regression tests mock paths; live integration deferred to deployment (REMEDIATION-ASSESSMENT.md)
